# App data and routing

The shell reads app metadata, database counts and Dashboard metric reports through `DataSource`. The UI does not calculate metrics; the Rust application assembles them from `xt-metrics`. DTOs are generated from Rust into `apps/desktop/ui/src/data/generated/`; regenerate and verify them with `cargo xtask dto-export` and `bash scripts/ci/check-dto.sh`. Generated files retain the generator's formatting.

## Selecting a source

Native Tauri always selects `TauriDataSource`, including when `VITE_XTRACE_FIXTURE` is set. Its `appInfo()`, `dbCounts()` and `nativeIndexStatus()` methods invoke the `app_info`, `db_counts` and `native_index_status` commands, and its `pullRequests()`, `refreshPullRequests(ids)` and `cancelPullRequestRefresh()` methods invoke the pull-request commands below; the last returns the generated `NativeIndexStatus` (phase, freshness, interpreter, bundled readers and each host's last scan), which the app also publishes on every change as the `native-index://status` event. Command and event names live in `src/data/ipc-names.ts`; components import the generated types and use query hooks rather than calling IPC.

For a browser fixture preview:

```sh
pnpm fixtures:export
VITE_XTRACE_FIXTURE=F1 pnpm dev
```

`FixtureDataSource` reads the generated `apps/desktop/ui/fixtures/F1.json` shell export. It returns copies of the same `AppInfo`, `DbCounts` and Dashboard report shapes used by native IPC. The export contains a portable `fixture://F1` label and canonical counts of 1 session, 25 records, and 15 usage rows. Its `emit(event)` helper delivers deterministic test events without timers or a simulated ingestion service. F2, F20, and unrecognized fixture names fail explicitly; they have no populated shell export.

The fixture adapter is dynamically imported only inside a Vite `DEV` condition. A production build ignores `VITE_XTRACE_FIXTURE`, even when it is set during compilation, and excludes the adapter chunk and fixture JSON. A browser without an enabled development fixture shows an explicit unavailable preview. It never falls back to sample data. Native fixture selection and temporary database ownership are enforced separately by the Rust application.

## Queries and events

`DataProvider` owns one active QueryClient for the window's selected source. Replacing the source remounts the query runtime, creating an isolated client and fresh query observers and warning state. Queries use a one-second stale time, no automatic retry, and no focus refetch unless a query sets its own policy. The account-usage query refreshes Codex at most every five minutes while visible and catches up after focus with stale data (a Codex result under a minute old is reused). It never starts a Claude read; it returns the Claude reading the app holds. While the app's first Claude read of a launch is still running (`reading`), the query checks back every three seconds, without starting Codex again. A background re-read keeps the shown values; only the first read and an explicit Refresh show the reading state. A Claude reading shows its original read time and is stale when it is fifteen minutes old, when the latest read failed, or when it was saved by an earlier launch and this launch has not read Claude yet. The shell's metadata consumers share `['app', 'info']`, `['database', 'counts']` and `['native', 'index']`, so reading the same data in the sidebar and Settings shares a cache entry. Refresh explicitly refetches the first two; the index status refreshes on its own event and, while it is transient (the initial scan or interpreter discovery), polls every second, since the one-time `ready` event can precede the listener's registration; when the status is first seen settled, or seen to settle after polling, the same query prefixes that event would have invalidated are invalidated. That record belongs to the QueryClient, not to a component: every route that reads the status shares it, so mounting or remounting a route does not invalidate again, and a settling event records it too, so the status query then seeing the settle does not repeat the event's invalidation. Ordinary stale-time refetches on mount are unchanged.

The provider registers each event once per mounted lifecycle. Listeners receive the event's payload unvalidated; only `native-index://status` reads it, as the published `NativeIndexStatus`. A single 500ms window starts with the first event; matching query prefixes are collected in a set. Continuous imports therefore refresh at bounded intervals rather than postponing refresh indefinitely. Invalidation restarts an active query's read that is in flight when the query already has data; a first read still in flight is joined rather than restarted, so it is read once more when it lands, and data committed before the event is never left as the final result.

| Event                          | Query prefixes invalidated                           |
| ------------------------------ | ---------------------------------------------------- |
| `ingest://import-received`     | `database`, `metrics`, `sessions`, `hosts`           |
| `ingest://backfill-progress`   | `database`, `metrics`, `sessions`, `hosts`           |
| `ingest://turn-completed`      | `database`, `metrics`, `sessions`, `hosts`           |
| `ingest://host-connected`      | `app`, `database`, `metrics`, `sessions`, `hosts`    |
| `rulebook://fire-received`     | `fires`, `rules`                                     |
| `prs://refreshed`              | `prs`, `gh`; keys below                              |
| `native-index://status`        | `native`, `database`, `metrics`, `sessions`, `hosts` |
| `store://content-purged`       | `sessions`, `metrics`                                |
| `sessions://creations-changed` | `sessions/list`, `sessions/one`, `metrics/dashboard` |

`sessions://creations-changed` carries no payload. The native index publishes it once after a background sub-session pass (between reconciliations) commits a change to stored creation relations: a relation newly recorded, or an accepted one first withheld as conflicted. A pass that only replays, abstains or reads nothing publishes nothing, and the event leaves the index status, its freshness and its reconciliation count alone. It re-reads only the Sessions list, the exact session row and every Dashboard range, whose rows carry the parent; the PRs report, the cached inventory and a pull request's linked sessions measure nothing a relation changes, and the drawer names no parent, so they are not re-read. Relations a scan changes arrive with that scan's own status event.

A `native-index://status` event whose status is `scanning` is initial-scan progress: it invalidates only `native`, so the status stays live while the data queries are not re-read, and restarted, on every progress tick. The scan's data is read when `ready` or `stopped` settles it; a lost settling event is covered by the status query as above. An event without a readable status invalidates every prefix in the table.

`prs://refreshed` also refreshes four narrower keys under prefixes it does not own: `['sessions', 'list']`, `['sessions', 'one']`, `['metrics', 'pr-analytics']` and `['sessions', 'pr-linked']`, because a committed refresh changes link titles and the cached facts the PRs report is computed from. Every ingest event, and a settled `native-index://status`, also refreshes the stored inventory `['prs', 'list']`, because committed indexing can add links; a `scanning` status does not. Nothing in any of these reads contacts GitHub.

These are structural query-key prefixes, not wildcard strings. Future screen queries must include all input dimensions, including range, in their keys. Tests exercise a harness query with reversed request completion; the old range's result cannot replace the current range. The Dashboard keys are `['metrics', 'dashboard', days]` and `['metrics', 'tokens-by-host', days]`, and the Sessions key is `['sessions', 'list', days, search, host]`, so every ingest and index status event above refreshes them, including a reconcile that enriches existing records without adding any.

## Stored content settings

`DataSource.retention` is present only on `TauriDataSource`; the browser fixture and preview sources omit it and Settings says the controls are unavailable. `read()` and `set(mode)` invoke `content_retention` and `set_content_retention` with the generated `ContentRetention` (`metadata_only`, the default when nothing is saved, or `full_content`). Settings shows only the mode read back after the write commits. `purge()` invokes `purge_stored_content`, which calls the store's existing `purge_content` with the default content registry (session titles, record content, tool input and the short message previews) in one transaction and returns the generated `ContentPurge`. The previews are the one text kept in either mode; Settings says so beside the mode. Settings calls it only from its confirmation dialog. The app emits `store://content-purged` only after a committed purge that cleared at least one field, and Settings invalidates the same prefixes from the committed outcome. A failed or empty purge invalidates nothing. The retention query key is `['settings', 'content-retention']`; neither command changes the other.

## Dashboard metrics

`dashboard(days)` and `tokensByHost(days)` invoke `metrics_dashboard` and `tokens_by_host` with `{ windowDays }`. Only 7, 14 and 30 days are accepted; other values fail before storage is opened. Both return generated DTOs (`DashboardMetrics`, `TokensByHost`).

- **Clock and zone.** The native app uses the system clock and time zone. Fixture mode uses the fixture manifest's pinned `now` and UTC, and reports `clock: "fixture"`. Fixture reports come from the same assembler as native reports, and `pnpm fixtures:export` writes all three ranges into `F1.json`. Reports never contain database paths.
- **One snapshot.** Current and previous windows (the previous window has the same length and ends where the current one starts), coverage, lanes and the lane sessions' context and measurements, and M-19 for both windows are read in one SQLite read transaction.
- **No shared wait.** Every metric read (Dashboard, tokens, Environment, Sessions, a session's row and stretches, PR analytics, Today and a span's detail) holds the app's state lock only long enough to take the clock, zone, metric context and database path (and the saved typing speed for the Dashboard, the stored repositories for Environment), then releases it and reads on its own read-only connection. A long Dashboard report therefore keeps no other command, such as a span's detail, waiting. SQLite's WAL mode gives each read its own snapshot, so reads never block each other or the native index's writes. Shutdown closes admission, then waits for the reads already running before it closes the database.
- **Tiles.** Each tile has fixed fields: `value`, `unit`, `rule_id`, a `reason` when the value is unknown, an optional `note`, sample counts and a `delta`. `null` means unknown; a measured zero stays `0`. `delta.pct` is in percentage points (`50` means +50%). It is `null` and `suppressed` when either window has fewer than five samples or the previous value is zero. The previous value is kept either way. Samples are sessions for session-derived tiles (token and cost tiles count distinct sessions with selected usage, not responses) and stretches for hands-off. Surfaces excluded from hands-off for unhealthy timestamps are listed in `hands_off_excluded_surfaces` with their qualifying and degenerate session counts. Agent hours per day divides agent hours by the number of local calendar days in the range, including empty days, partial first and last days, and DST days. The tile's `note` states the divisor.
- **Days.** `days` contains one entry per reported local calendar day in the selected range, including empty and clipped days. `agent_hours` allocates measured M-05 spans across day boundaries. `human_hours_est` sums M-07 counted input characters on each message's exact timestamp day and divides by the saved typing rate. Each series adds back to its Dashboard total. Human time is unknown on every day if any eligible input lacks classification or length; agent time remains measured. A measured zero stays `0`.
- **Your hours and leverage (M-08).** `human_hours.current` is "your hours" over the whole local days the selected range touches: `start_ms` is the first day's local midnight and `end_ms` the midnight after the last day, so a 7-day range has 8 whole days when it starts mid-day. `by_day` has one whole day per entry, with the same dates as `days`, each with its stretches. Two consecutive messages you sent at most `break_minutes` apart (the saved break length, default 60) count the whole gap; a longer gap is a break; stretches are split at local midnight, and a message with no other within the break length is a zero-length stretch. Messages up to one break length before a period are read too, so a stretch that began the evening before keeps its part after midnight. `messages` counts your messages inside the period. `previous_active_ms` is the same total for the same number of whole days just before, from the same timeline, so a stretch over the boundary is split between the periods. An unknown sender classification inside a period, or within a break length before or after it, makes that period `null`. `leverage.agent_ms` and `leverage.previous_agent_ms` are agent hours (M-05) over exactly the same whole days as the two periods of your hours, and `leverage.by_day` gives each whole day's agent hours, your hours and leverage (`null` when your hours are zero or unknown). `tiles.leverage` divides `leverage.agent_ms` by `current.active_ms`, and `leverage.previous_agent_ms` by `previous_active_ms` for its change, so both sides always cover the same span (the Effort chart's agent hours stay on the rolling range); it is unknown when your hours are zero or unknown, and its reason says whether you sent no messages or each message stood alone. The typing-based ratio tile was removed. `concurrency_by_day` measures each day as its own window; `hands_off_by_day` groups the range's own hands-off stretches (one load and one timestamp-health judgement for the range) by the local day of the message that starts each one.
- **Lanes.** Activity lanes always cover the most recent 48 hours (`lane_start_ms`–`lane_end_ms`), whatever range is selected. They are sorted by end, then start (both descending), then session and host, and capped at 200 rows. `lanes_total` and `lanes_truncated` report the cap. The cap affects only which rows are displayed; concurrency and other aggregates use every span.
- **Lane sessions.** `lane_sessions` holds one entry per distinct session the returned lanes name, in identifier order: `session_id`, `host`, the indexed `repo` (the recorded repository, else the working directory) and `branch`, the nonblank saved `title` Sessions shows, `started_at_ms`, `pr_links` and `inferred_pr_links`, `cost`, `parent` (below) and `known_child`. Repository, branch, title, start and cost are independently nullable; `null` is unknown and a measured zero stays `0`. The start is the start the host recorded, whenever it was. Claude Code records no start, so a Claude session without one starts at its earliest imported message (in a forked session that can be a message copied from the session it was forked from). Another host with no recorded start stays `null`. The start is never a returned span. `pr_links` counts distinct canonical pull requests the session has a stored link to at every evidence level (exact, sha, inferred), over all indexed time and whatever their merge or refresh state — the same recorded links Sessions lists — with the inferred-only part in `inferred_pr_links`; an indexed session with no link reads `0`, and both are `null` only when no context row was found. These are read in the same one bounded context statement, keyed on the link table's primary key. `cost` prices the whole session's selected responses, whenever they were — the 48-hour lane window only decides which sessions are listed — so neither that window nor the display cap reduces it; a response with no recorded time, which no window holds, is counted as unpriced with the reason `missing_timestamp`, so such a session's total is a floor rather than silently short: `total_usd` (`null` unless every selected response was priced), `priced_subtotal_usd`, the selected, priced, unpriced and assumed-tier (Codex, no service tier recorded, priced at OpenAI's default (standard) tier) response counts, and `unpriced`, the unpriced responses by model, service tier and reason in the cost report's own `DashboardUnpriced` shape. It uses the cost tile's own selection, deduplication and price catalog (`MetricsDb::whole_session_costs`, the same `v_response_usage` rows restricted to the session but not to a window; it is the only per-session cost read), so it is never a second pricer; a lane cost can exceed the selected range's cost tile, since it includes the session's work before the range. A response belongs to the session that owns its record: a Claude Code sidechain (subagent) counts with its parent session, and a separately indexed sub-session counts on its own row. For a returned session `cost` is `null` only when no indexed user session owns the identifier; an indexed session with no selected response reads zero selected responses and no total. No source file is read: the context is stored session metadata, read by identifier in the dashboard snapshot. The host titles the card shows for rows in view come from a separate on-demand read (`titles.read`, [session-titles.md](acceptance/session-titles.md)) and never enter the report. `known_child` is `true` when stored positive evidence says another session created this one: an accepted creation relation, an unconflicted saved Human session origin, or an accepted child fact, bound to the session's exact canonical ID, host and native ID. The first two are the conditions the Human input view uses to count the session's user messages as an agent's; a child fact is not, so a session known only by a child fact is a known child whose user messages that view still counts as typed. A child fact says only that an agent created the session, never which one: the native index records one, before and apart from any parent, when a Codex thread's own verified header is typed as a spawned or Guardian subagent (whatever its parent fields say), when a Codex agent's recorded create-mode Claude launch named and acknowledged a fresh saved child, or when a Claude agent's own `Bash` call launched a Claude print session that is the one possible child of that launch by its exact first input, folder, birth within the call and whole printed answer (see `crates/xt-store/src/child_fact.rs`). A launch claimed for two children, or with two possible children, withholds the facts resting on it, and only those. It is read independently of `parent`, so a known child whose parent is unindexed, ambiguous or unknown is `true` with a `null` parent; a conflicted relation or origin, a withheld child fact, or one no longer bound to the session's identity, does not set it on its own, though another valid fact still can. An ordinary session without a title, live status or parent is `false`. It is `null` only when no context row was found, and the generated TypeScript marks the key optional (`known_child?: boolean | null`), so an older report without it reads as not known. Beside the returned sessions' entries, `lane_sessions` also holds one context-only entry for each indexed parent those entries' own `parent` names that the lanes do not, read in the same snapshot in one more bounded statement (deduplicated, never more than the returned sessions, within the store's 200-identifier context bound). Such an entry has no lane, no span and no measurement — its `cost` is `null` — and its own `parent` is whatever its context read resolved; no further ancestor is read. The list is therefore at most twice the returned sessions. These entries exist only so the Dashboard can tell whether an unreturned parent is itself a known child with no verified parent; an entry never makes a row by itself.
- **Older sub-sessions.** `lane_sub_sessions` holds every verified sub-session, at any depth and whenever it ran, under a session the lanes name, that the lanes do not name themselves, so the Dashboard can list a group's every sub-session and add up its total. Each entry has the same shape as a `lane_sessions` entry — context, its own `parent` (a listed session or another entry here) and its whole `cost` — read in the same snapshot. The walk (`MetricsDb::sub_sessions`) goes level by level through accepted creation relations and unconflicted native reviewer origins, keeping a candidate only when the same parent resolution every list uses (`session_list::parents`) names a session of the level above; it never adds a lane, span or listed session. Nearer levels come first, each most recently active first, at most 1,000 (`SUB_SESSION_LIMIT`); every one found beyond that is counted on the listed session whose walk found it, as `sub_sessions_not_shown` (`null` when none), and the Dashboard says so and keeps the total a floor. Entries come in the walk's order, so a parent always precedes its own sub-sessions (the Dashboard places them by parent, whatever the order). The walk stops after 20,000 sessions; a listed session whose walk that cut short has `sub_sessions_cut_short: true` (else `null`), and its count is then a lower bound, possibly `null` with some left out. On the live history at the time of writing the largest group had 327 sub-sessions.
- **Sub-session parents.** Each Sessions row (list and exact detail) and each `lane_sessions` entry carries `parent`: the session that verifiably created it, or `null`. It is `{session_id, host, title, evidence}`, where `session_id` is the parent's exact canonical identity (its own row and detail route), `title` its saved title as its own row reads it, and `evidence` the closed kind of proof: `native_spawn`, a Codex thread whose own opening `session_meta` (`payload.id` the child) names a distinct full parent thread (`source.subagent.thread_spawn.parent_thread_id`), with `payload.session_id` naming the root of its spawn tree (a full thread other than the child; the parent itself only when the parent is a root, and never read as the parent) and any explicit `payload.parent_thread_id` naming exactly that same parent (a `session_id` alone never proves one); or `agent_launch`, a Claude session a Codex agent launched: either with a recorded foreground `claude -p` command, whose own process completed successfully, whose redirected JSON result named the child and was then read by the parent, and whose first saved user input carries text that is exactly what the launch submitted; or with a recorded `claude -p --session-id <child>` command in the agent's own `exec` operation, which the host acknowledged with that operation's own process result (any exit code, or a running process; the job's later success or failure does not matter), and whose child is a fresh saved session whose first saved user input is exactly the command's one literal prompt, dated at or after the launch ([claude-launch-links.md](acceptance/claude-launch-links.md)). Neither names a role or task. It is present only when that stored relation is accepted and its parent's host and native identity resolve to exactly one indexed user session other than the child; an unindexed, ambiguous or conflicting parent is `null`, never a guessed link. It is read in the same snapshot as the row, for the rows or lanes already returned: it never adds, removes, reorders or moves a row, lane or span, never changes a cursor, search result or measurement, and a parent filtered out, on another page or outside the lane window is linked, not added (outside the lane window it gains only the context-only `lane_sessions` entry described above, never a lane). The Dashboard's compact Sessions table arranges the lanes it was sent by it — each child under its parent's row, or under one row naming a parent outside the window, which gains no lane or measurement ([dashboard.md](acceptance/dashboard.md)) — and the Sessions page arranges its loaded rows and its recent activity the same way ([indexed-sessions.md](acceptance/indexed-sessions.md)); the reports themselves keep each child its own row. Each Sessions row (list and exact detail) also carries `known_child`, the same bit and meaning as a lane session's, read in the row's snapshot (`known_child?: boolean | null` in TypeScript, `null` only when no context row was found). Each Sessions page carries `referenced_parents`: context only for each indexed parent its rows' `parent` names that the page does not list itself — `{session_id, host, known_child, parent}`, in identifier order, read in the same snapshot by the same bounded context read (at most one per row, so 50); its own `parent` is whatever that read resolved and no further ancestor is read. An entry has nothing measured and never makes a row; it lets the page tell whether a parent on a later page or outside the filters is itself a known child with no verified parent. TypeScript marks the key optional (`referenced_parents?: …`); native and fixture pages always send it. The generated TypeScript marks the key optional (`parent?: … | null`); native and fixture reports always send it. Native spawns are recorded from source headers by the native index (see `crates/xt-ingest/src/native/session_creation.rs`). Explicit-session launches are recorded automatically by the native index's background passes (`crates/xt-ingest/src/native/claude_launch/`, through `Store::record_claude_launch_guarded`); result-file launches only through a separate trusted store method a validator calls after proving that chain (`Store::record_cli_artifact_creations`), which no ingestion path or app command calls. Neither confirms or reclassifies any single input; as for every accepted creation relation, the Human input view counts the child session's user messages as the creating agent's, not a person's. For those relations the store keeps the structural identifiers of the chain (the exact canonical parent, the child's first input record, the launch call and operation, the process handle, the completion and read calls, and the result's own identifier, which this version requires); every valid proof first claims its launch operation, so a second child claimed for one launch, even one whose stored relation holds a different launch, or a second different chain for one child, withholds every claim it contradicts, for good. No prompt, command, path, output, digest, task path, role or title is stored for any relation.
- **Coverage and cost.** Usage coverage and session capture coverage are reported separately (`pct` is 0–100). `capture_inventory` stays `unknown` because the app does not yet supply a runtime discovery inventory. Capture receipts and native index status do not change it. Cost is labelled API-equivalent and includes the price version, `as_of` date and basis. `total_usd` is `null` when any selected response is unpriced; `priced_subtotal_usd` and the named unpriced reasons (for example, a missing service tier) are reported separately.
- **Untimed history.** `untimed_history` counts the eligible canonical records that state no timestamp, read in the same snapshot as everything above. It is the only part of the report with no window, and cannot have one: a record with no timestamp is in no local day, so no range includes or excludes it. The projection is `v_records` — the records every other metric would have measured had they stated when they happened — taken before the timestamp requirement `v_session_events` applies. The work exclusions still apply first, so a meta record, a judge session's record or a `<synthetic>` model row is never reported as a record that merely lacks a timestamp, and copied native records are counted once, as the work totals count them. `records` is the sum of `by_surface`, one row per host and raw surface in host then surface order, with `null` left as an unknown surface and no row for a pair with no such record. Zero is a measured zero. No timestamp is inferred or repaired, no share of anything is reported, and a count above zero is not a claim that a host is failing.
- **Merged pull requests and effort (M-19).** `pr_effort` carries `xt_metrics::PrEffortReport` field for field for the selected window (`current`) and the previous window's tile (`previous`), read with `confirmed_only` on: inferred links are removed before eligibility, markers and assignment, so exact and SHA links count. Only cached refresh facts are read; nothing here requests anything or applies an age cutoff. The tile counts distinct retained pull requests whose cached state is `MERGED` at a precise `merged_at` inside the window; `merged` is that count only when `complete`, otherwise `null`, with `known_merged` a subtotal and `unknown_facts` the pull requests whose facts cannot decide it. `freshness` counts never-attempted, refreshed, failed-never-refreshed and failed-after-refresh rows; a failure after a success keeps that success's facts. `markers` list each merged pull request once on its local merge day. `by_assignment` is disjoint: every session with in-window work, linked or not, appears once under one canonical type, `mixed`, `other`, or `unresolved` (a disclosure, not a type), and the groups add up to `cohort`. Cost (`cost`, the cost report's summary shape) prices the global M-04 response selection on each response's event day exactly as the API-equivalent cost does, so the cohort and each day equal that report: `total_usd` is `null` (never `0`) once a selected response is unpriced, `priced_subtotal_usd` covers only the priced ones, `unpriced` names each model, tier and reason, and `assumed_tier_observations` counts Codex responses priced at OpenAI's default tier because none was recorded; agent time is M-05 allocated by local day. Every day also carries `models`, that day's split by model in name order (`null` first), which adds up to the day exactly: `priced_nano_usd` (the exact priced subtotal in nano-USD), `priced_observations` and `unpriced_observations` of the responses that named the model, and `agent_ms` of the sessions whose most-used model over the window is this one (most selected responses, then most output tokens, then the first name); `model` is `null` for responses without a model name and for sessions with no response that names one. The Dashboard's Effort card draws `cohort.by_day` (day totals and their models) and `markers`; it draws no assignment. `tiles.merged_prs` (rule `M-19`, unit and samples `prs`) states the same tile: its value is `merged`, its reason names the known subtotal and the unknown count, and its delta compares two complete counts of at least five.
- **Unavailable sections.** Rule fires and environment are listed in `unavailable` with reasons; they never report zero. The Dashboard report's `environment` entry stays: Environment data is a separate command, below.

Integers above JavaScript's safe range and non-finite values fail the command rather than being rounded or turned into `null`.

Cleanup cancels the timer and query promises, releases installed listeners, and immediately releases listeners whose asynchronous registration finishes after cleanup. Late callbacks cannot invalidate a disposed client. A subscription failure produces a controlled live-update warning without backend error text. `connected` means only that every event is heard from then on. It does not say that anything cached was read since: when all listeners have registered the runtime raises a per-client count, `heardEpoch`, synchronously, before its catch-up reads begin and before it announces `connected`, so a reader can tell a read that began after the listeners registered from one that began before and merely answered after. The sidebar's status row is the one reader that needs this; it stays last known until such a read has been accepted. Query cancellation prevents late cache updates; it does not promise to abort an already-running native command.

## Lane span detail

`spanDetails.read(sessionId, startMs, endMs, readId)` invokes `metrics_span_detail` with `{ sessionId, startMs, endMs, readId }` and returns the generated `DashboardSpanDetail` for one activity-lane span, named exactly as the Dashboard report's `lanes` entry names it (both endpoints inclusive). `spanDetails.cancel(readId)` invokes `cancel_metrics_span_detail`; the bubble cancels a read still running when it closes or its bar unmounts, and the cancelled answer is discarded. Only the source read for the words takes one of the span reads' eight slots, after everything else is measured, so a busy moment never withholds the tool or output: the words alone answer `busy`, and an answer that is `busy` or cancelled is not kept, so the next open asks again. The Dashboard reads it only while a span's bubble is open, under the query key `['metrics', 'span-detail', purges, sessionId, startMs, endMs]`, where `purges` counts the committed content purges the window has heard of: committed-data events re-read it, a content purge drops it (see Kept previews below), and opening the same span again reads nothing. A request that names no session, is inverted, or is longer than the 48-hour lane window is refused before storage is read.

- **Most-used tool.** `tool` is M-17's record-bound tool calls inside the span, by stored name, a tie going to the first name in order: `called` with its count, `no_calls` when every record in the span states its calls and they sum to zero, else `unknown`.
- **Output.** `output_tokens` is the M-04 slice of the span's interval, exactly as Sessions slices a window: a response restated over several records counts once; `null` when no selected response stated the counter.
- **Last prompt.** `prompt` is the latest record at or before the span's end that the stored M-02 classification calls a person's message, so sidechain, injected, confirmed automated, Claude Code task-notification and sub-session inputs are never chosen: `found` with its time and whether it is inside the span, `unclassified` when the newest candidate cannot be classified, or `no_message`. Its words (`text`) are the index's own when content retention kept them, else the short preview the index keeps of a person's message (below). Only when neither exists are they read from the session's original source through the same resolution, generation check, ceilings and pinned reader a transcript open uses, after the database is released, and the record is picked by its saved identity alone: `stored` (one line of at most 280 characters, whitespace collapsed), `not_found` when the source holds no record with that identity (no other message is shown instead), `ambiguous` when several records in the source carry it (a fork copies records) and they do not say the same thing, `wrapped` when an accepted human-input adjustment says only part of the record is the person's (a Codex question reply or image wrapper: nothing locates that part, so no words are shown, whether kept or not), `busy` as above, or `unavailable` with the same reason a transcript open would give (for example `replaced` when the file changed since it was indexed, or `not_indexed` in fixture mode). The words read from a source are held in memory for the answer and the view's per-span cache only; nothing is written to the database or to disk by the read.
- **Automatic line.** `automatic` is the latest input inside the span (same session, not a sidechain, both endpoints inclusive) that a stored source proof says Claude Code wrote as a task notification — the line it adds when a background agent, command or monitor finishes, marked by the line's own `origin.kind`: `found` with its time, or `no_notification`. Its words are the notification's own `<summary>` (the first one ahead of any `<result>`), as one line of at most 280 characters: `stored`, or `no_summary` when it has none. They come from the index when content retention kept them, else from the summary's kept preview, otherwise from the same source read as the prompt's words — one read serves both — with the same `not_found`, `ambiguous`, `busy` and `unavailable` states. The bubble shows it after the `›` line as a muted `(Automatic) <summary>` line, never marked `›`, and shows nothing for any state but `stored`.

- **Kept previews.** Whatever the retention mode, the index keeps one short preview per input in `record_previews` (migration 17): for an input the stored classification called a person's whole message when it was indexed, its `text` blocks joined as the classifier joins them; for a proven task notification, its own `<summary>`. Each is one line, whitespace collapsed, at most 280 characters, with whether more followed. It is written in the ingest batch's own transaction, so a rejected input or batch keeps none, and never for an assistant reply, sidechain, tool result, meta record, command, interruption, system reminder, an input whose classification is unknown, a conflicted record, or an input a human-input adjustment says is only partly (or not) the person's (a Codex question reply, image wrapper, heartbeat or injected skill body; the reader marks these before the write, and an adjustment applied later removes any person preview). A replay never rewrites a row. The bubble still chooses the record by the current classification first and only then reads its preview, so a proof that later makes a record automatic hides its preview. Previews are filled for Claude, Codex and Cursor; migration 17 clears the Claude transcript checkpoints once so the next scan reads unchanged Claude history again to fill them (Codex and Cursor are read whole every scan). "Delete stored content" clears them; a cleared preview is not refilled for the same record, but messages indexed afterwards get new previews, and previews cannot be turned off. A purge also raises the UI's purge epoch, which keys every span detail: reads still running are cancelled and every answer read before the purge, cached or late, is dropped, since metric reads no longer wait for the purge to commit. No report, export, log or fixture carries previews, except the bubble's own answer; like all stored content they are in copies of the database (the backups an install makes included), and a delete does not erase those copies or database free space.

Fixture exports include `span_details` for every span the fixture's lanes return, produced by the same command path.

## Environment

`environment(days)` invokes `metrics_environment` with `{ windowDays }` and returns the generated `EnvironmentMetrics`. Only 7, 14 and 30 days are accepted. Its query key is `['metrics', 'environment', days]`, so every event that refreshes the Dashboard refreshes it too, including enrichment that adds no record.

- **Two disclosed windows.** `window` is the selected range. `strip_window` is fixed: exactly 14 local calendar dates ending with the date that holds the last instant before `now` (the current, possibly partial, local day), starting at that first date's local midnight. Both use the same clock and zone (system, or the fixture's pinned `now` and UTC) and are read in one SQLite snapshot. `selected` and `strip` are the M-17 reports for those windows, preserving raw optional surfaces, unknown identity details and unresolved reasons, including `hook_attribution` for stop-hook summaries.
- **Unknown inventory.** `inventory` is always `unknown`, and each host's M-17 join is `unknown`. The configured components beside it cannot prove a complete callable inventory, so the report contains no not-installed, never-called or used/installed figure and a consumer must not derive one.
- **Rows Rust orders.** `identities` has one row per host and identity (summed over surfaces), with the selected-range `calls`, `strip_calls` and 14 `strip` buckets. `order` sorts by selected calls, then strip calls (both descending), then host and identity. A top slice and the full list are taken in that order; React does not recount.
- **Configured facts.** `configured`, `sources`, `cache` and `roots` are the probe reading described in [Environment probe](ENVIRONMENT.md). They carry names, counts and statuses only: no path, command, argument, environment value, credential or URL.

Fixture exports include `environments` for all three ranges, produced by the same assembler over the F16 synthetic probe matrix. Integers above JavaScript's safe range fail the command.

## Sessions

`sessionsList(search, host, after, windowDays)` invokes `sessions_list` with `{ search, host, after, windowDays }` and returns the generated `SessionPage`. Only 7, 14 and 30 days are accepted, validated before storage is opened.

- **One snapshot.** The metadata page and every row's measurements are read through the metrics connection inside one SQLite read transaction, so a row cannot be shown beside numbers taken after the native writer appended to it on its own connection.
- **Unchanged paging.** Search, host filtering and descending time/ID pagination remain the store's, 50 rows per page with an opaque `next` cursor.
- **Explicit window.** `window` is the same `DashboardWindow` shape the Dashboard reports (`days`, bounds, zone and clock). Measurements describe that window's events, not whole sessions; the Shell's selected range supplies it, and the TopBar presets and period label are shown on Sessions for that reason.
- **Per-session measurements.** Each row carries `metrics`, mirroring `xt_metrics::SessionWindow`: `{"state": "missing"}` when no indexed session owns that identifier, otherwise `{"state": "indexed", events, human_messages, tokens, agent_ms}`. They come from the same projections the Dashboard reads — global M-04 response selection and copied-record deduplication happen inside those projections, before the session and window filter — so a row is a slice of the Dashboard's totals, never a re-derivation.
- **Each measured column states its rule.** `Human msgs`, `Tokens` and `Agent min` headers are `RulePopover` buttons quoting M-02, M-04 and M-05 from the reviewed rule contract, reachable by keyboard and dismissed with Escape. The label is the trigger, so a measured column is no wider than an unmeasured one, and the grid's `columnheader`/`cell` roles tie every number to its definition.
- **The same untimed disclosure.** Sessions reads the Dashboard's `dashboard(days)` report for its range summary, so it states `untimed_history` in the same words the Dashboard does. The rows below it are dated too, so no search, host filter or page can hold that history either; the count is of all indexed history and changes with neither the range nor the table's filters.
- **Records and measured work differ for a fork.** The `record_count` column counts records visible in that session, including copies inherited from a forked session; copied work is measured once under the session that owns it, so a copied session's measured columns are legitimately lower. This is the same deduplication the Dashboard totals use.
- **Unknown, zero and missing stay distinct.** A session with no events in the selected window reports `events`, `human_messages` and `agent_ms` as a measured `0`; its M-04 counters stay `null`, because M-04 has no selected response to measure. `human_messages` is `null` when a record's classification is unmeasured. A session that is not indexed reports `missing` and no numbers at all.

Fixture exports include `sessions` for all three ranges, produced by the same assembler as the native command. Integers above JavaScript's safe range fail the command.

## Pull requests

`pullRequests()`, `refreshPullRequests(ids)` and `cancelPullRequestRefresh()` invoke `prs_list`, `prs_refresh` and `prs_refresh_cancel`, and return the generated `PrList`, `PrRefreshReport` and a boolean. The `/prs` page's Cached inventory view lists what `prs_list` holds ([acceptance](acceptance/cached-pull-requests.md)); its default view is the merged-PR report below ([acceptance](acceptance/pr-analytics.md)). The refresh has no screen beyond the Dashboard control below.

**Automatic checks, and the manual refresh.** The app also checks pull requests on its own, read-only, through the same bounded batch: when its main window gains focus, when the Dashboard is shown (`prAutoCheck.request()`, `prs_auto_check`) and about once an hour. An automatic run picks the linked pull requests that were never checked, then the ones last seen open whose last check is at least an hour old, newest stored first, in batches of at most 20 and at most five batches per run. Merged and closed pull requests are final and never checked again automatically. A run that finished within the last ten minutes is not repeated on focus, unless a pull request that was never checked appeared after a run that went cleanly. A missing GitHub CLI, an attempt that cannot start, or a signed-out one pauses automatic checks until the next launch or a manual refresh. Signed out is read only from gh's documented "authentication required" exit code (4, `gh help exit-codes`), which the client reports as `unauthorized`; every other nonzero gh exit is `execution_failed` and never pauses. Three failures before any success stop that run as a cost cap (an offline host, an outage, a broken gh), and a later run tries again. Pull requests whose last check failed (another account's repository, a deleted pull request) are checked after never-checked and open ones. A failure after a success in the same run never stops it. A rate limit ends that run. A manual batch cancels a running automatic batch and waits for it (within the shutdown bound) instead of being refused. `prs_auto_check_status` (`prAutoCheck.status()`, the generated `PrAutoCheckStatus`) reports whether a run is checking, why it paused and when it last finished; the `prs://auto-check` event (no payload) announces each change and re-reads the status and the `metrics/dashboard` reports. Setting `XTRACE_PR_AUTO_CHECK=off` switches automatic checks off for a launch; the manual refresh is unchanged. Native fixture mode's automatic check uses the same synthetic source as its manual refresh, and the browser fixture has no automatic check.

- **Stored identifiers only.** `prs_refresh` accepts the stored pull-request IDs `prs_list` reports, never a URL, repository or executable path. The backend resolves each ID to its canonical identity itself and refuses one that storage does not hold or that no session links any more. A selection is 1–20 distinct positive IDs; anything else is refused before storage is read.
- **One batch, bounded.** Batches are sequential and never overlap: a second `prs_refresh` while one runs is refused rather than queued. A batch has 120 s in total and each attempt at most 30 s, and never more than the batch has left. Identities are resolved under the state lock, which is released before the first process starts, so every other command keeps answering while a refresh is blocked; the lock is reacquired only to persist one result.
- **Cancellation.** `prs_refresh_cancel` stops the running batch, before it starts, between two attempts or during one, and returns false when none was running. Pull requests the batch did not reach are reported as `skipped`, never as `failed`: nothing ran for them and nothing was written for them. Quitting cancels a running batch before the database closes, and storage refuses a write once it is closed.
- **Typed outcomes.** `requested` equals `attempted + skipped`, and `attempted` equals `succeeded + failed`. Each row carries the canonical identity and either an executed outcome (`succeeded`, or `failed` with one of storage's closed failure codes) or a `skipped` reason. Reports and rows carry no executable path, command line, environment value, credential, process standard error or raw response body.
- **Execution and persistence are separate.** `attempted`, `succeeded` and `failed` report what the attempt did. Beside each executed outcome, `persistence` reports what storage then did with that result: `recorded` with the write (`applied`, `unchanged`, `stale`), or `not_recorded` with the reason (`storage_closed`, `refused`, `unusable`). Only storage's own validation vocabulary — an equal-attempt conflict, an identity it no longer holds, a result its rules reject — is `refused`, and the batch goes on. A database failure (SQLite I/O, corruption, a full disk, undecodable data, an incompatible schema) is `unusable`: like a closed database, it stops the batch, and every pull request after it is skipped as `storage_unavailable` with no further request made. An attempt whose result storage would not keep is still attempted and still succeeded or failed; `unrecorded` counts how many of them there were, so a screen can say the result was not stored rather than that nothing ran. Only `skipped` means nothing ran.
- **Storage reads are one snapshot.** The listed rows and their `linked_sessions` counts come from one SQLite read, so a pull request's metadata and its link count are always from the same instant even while the native index writes through its own connection.
- **The GitHub CLI.** The executable is resolved per requested batch from `XTRACE_GH` (an absolute path, backend only), then `PATH`, then the documented standard install directories; it is never supplied by the frontend, discovered through a login shell or probed by running it. A missing GitHub CLI is an actionable refusal that writes nothing, not an authentication flow the app offers to start.
- **Events.** A batch emits `prs://refreshed` once, after it has committed at least one change; a batch that changed nothing emits nothing. The event invalidates the `prs` and `gh` query prefixes, as in the table above. The Dashboard's refresh operation also re-reads the `metrics/dashboard` reports, and only those, when its batch reports `committed`, because committed facts change M-19; other metric queries read nothing a refresh writes. It uses the same `refreshQueries` as the event map, so a Dashboard read that began before the commit and had no cached data is read once more when it lands: the report shown is always one read after the commit.
- **Fixtures.** F1 declares three synthetic pull-request links in its manifest (`input/pull-requests.json`), seeded into its database as links only — refresh-owned metadata is never declared, because a link never sets it. Native fixture mode answers with deterministic synthetic outcomes stamped with the fixture's pinned instant, and never resolves or runs a GitHub CLI, reads a credential or makes a request. The pull-request number picks the answer, so a fixture shows an open, a merged and a rate-limited refresh without declaring any of them.
- **Browser fixture.** `pnpm fixtures:export` writes `pull_requests`, `pr_refresh` and `pull_requests_refreshed` into `F1.json`, produced by the application's own batch over the fixture database. `FixtureDataSource` lists the first, answers `refreshPullRequests(ids)` from the exported rows of exactly those identifiers (an identifier the export does not hold is `not_stored`), then lists the refreshed rows for those identifiers only, and emits `prs://refreshed` through the same event map when the report committed. It derives the report's counters itself; a test checks that derivation against the exported report for the whole selection, so the two accountings cannot drift. Refreshing a pull request again replays it as native fixture mode does: every fixture attempt is stamped with the pinned instant, so the same result at the same time is `unchanged`, commits nothing and emits no event, while a new pull request in the same selection still applies. `cancelPullRequestRefresh()` is always false: a fixture refresh is over by the time it returns. A populated fixture that links no pull request exports empty `pull_requests` and `pull_requests_refreshed` and a report that attempted nothing; the user's refresh command still refuses an empty selection.
- **Browser fixture and M-19.** The exporter reads `dashboards` before any refresh, as a fixture database starts. `pr_effort_states` holds, for every non-empty subset of the listed pull requests, the pull requests refreshed (`PrRef`, ascending ID) and each range's `tiles.merged_prs` and `pr_effort`, read by the same assembler after the application's own fixture batch refreshed exactly that subset on a freshly built database. The export refuses a fixture that links more than four pull requests rather than leave a selection without a state. `FixtureDataSource.dashboard(days)` serves the unrefreshed section until the preview refreshes something, then the state for exactly the pull requests it has attempted; each synthetic answer is fixed and stamped with the pinned instant, so a sequence of partial refreshes ends in the state of their union. A state the export does not hold fails the read instead of showing invented numbers. Native fixture mode recomputes, and `tests/fixture_mode.rs` checks every exported state against it byte for byte. Because the Dashboard is confirmed-only, refreshing the inferred #13 never changes F1's M-19. F1's synthetic merged pull request merges at the pinned instant, which is the window's exclusive end, so F1 never shows a merged pull request in its windows; synthetic UI cases cover that.
- **Dashboard control.** The Effort card's header shows a small red ! only when the pull-request checks need the user (a failed last check, automatic checks paused by gh, or automatic checks off with pull requests never checked; `prAttention` in `pr-effort.ts` decides it), and nothing otherwise; clicking it opens the refresh dialog, which first states the confirmed-linked refresh status. Only opening its dialog lists pull requests (`pullRequests()`), and only its Refresh button starts a batch of at most 20 stored identifiers the list holds from there. The dialog states that the request is a read-only `gh pr view` of title, state, merge time, size and head branch with the existing GitHub CLI sign-in, that the app also checks on its own, and the batch and attempt limits. The Merged PRs tile says in words how many linked pull requests are not checked yet (or that it is checking) instead of showing a number it cannot know, and its tip explains the tile in plain words rather than the M-19 rule text, which the Effort card keeps. The batch is owned by the source runtime (`DataProvider`'s `usePrRefresh`), not by the Dashboard: its progress, Cancel and final report survive a range change that replaces the report and leaving and returning to the Dashboard, a second batch cannot be submitted while one runs, and a replaced source starts with none and ignores the old batch's late answers. Each row shows its stored status, including stale facts after a failed refresh; the batch report and each row's outcome use the typed codes only.
- **Preview.** A browser without an enabled development fixture stays explicitly unavailable for these commands, like every other native one.

## PR analytics transport

`pullRequestAnalytics(days, confirmedOnly)` invokes `prs_analytics` and returns the generated `PrAnalyticsPage`: the preset `window` and the core `xt_metrics` per-PR report (`MetricPrAnalyticsReport`, Metric-prefixed so it never collides with the inventory's `PrRow`/`PrList`). One instant is captured under the state lock; the window ends at it and the fixed trailing-14-day token gate is anchored to it (`report.now_ms == window.end_ms`). Every row value, count, median, unknown/no-sample count, exclusion and gate reason is the core's, converted field for field; nothing is computed in TypeScript and rows are never summed.

`pullRequestSessions(request, after)` invokes `prs_sessions` with `{repository, number, confirmedOnly, windowDays, windowEndMs, after}` and returns the existing `SessionPage`. It lists every indexed user session with a stored link to exactly that canonical pull request after the confidence filter — linked membership, not activity, so a member idle in the window is listed with its empty measurement. The store applies the membership in SQL before the 50-row page bound and the cursor, through keyed lookups on the link and `(repo, number)` keys; rows, links and measurements come from the Sessions assembler in one read snapshot. The window is the preset ending at `windowEndMs`, which the caller takes from the displayed report's `window.end_ms`; the command never reads the clock, so every page of one drilldown measures the report's window. The preset, canonical identity (`owner/repo` is compared case-insensitively, the same number in another repository is another pull request), JavaScript-safe integers, anchor and cursor are all checked before storage is opened. Neither command refreshes, reads a transcript or source history, or contacts GitHub.

Keys: `['metrics', 'pr-analytics', days, confirmedOnly]` and `['sessions', 'pr-linked', repository, number, days, windowEndMs, confirmedOnly]` with the cursor as an infinite query's page parameter. Both inherit ingest, index-status and reconnect refreshes from their top-level prefixes and follow `prs://refreshed` through the keys above; a read in flight when a change commits is followed by one more read. The cached inventory `['prs', 'list']` follows ingest events and a settled index status through its own key, as above.

Fixture exports carry `pr_analytics` (each range and mode, before any refresh), `analytics` in every `pr_effort_states` entry, and `pr_sessions` (each listed pull request, range and mode, pinned to the fixture instant, read before the refresh so titles come from the current PR state). `FixtureDataSource` serves exactly those and refuses any request the export does not hold. F1's merged pull request merges at the window's exclusive end, so F1's report has no rows in any state.

## Recorded rule activity transport

`ruleActivity.read(readId)` invokes `rule_activity_read` with `{readId}` and nothing else, and returns the generated `RuleActivityResult`; `ruleActivity.cancel(readId)` invokes `rule_activity_cancel`. The native side reads one bounded snapshot of the default local rulebook's ledger (`~/.config/memhub-plugin/rulebook` under the native home startup selected) over the fixed trailing 14 × 24 hours, which it anchors when it admits the read. No root, path, range or filter crosses the boundary, and nothing reads it on an event, focus, timer or at startup; `rulebook://fire-received` is not its producer. No page reads it yet ([acceptance](acceptance/rule-activity.md)).

- **One read at a time.** A second read under any identifier answers `busy` at once and reads nothing; the running read is neither shared nor replaced. The read runs on the blocking pool and holds no database lock. Quitting refuses new reads and cancels the running one before the database closes, waiting at most three seconds.
- **Typed states, never error text.** `loaded`, `unavailable` (part and fixed reason), `source_changed`, `interrupted`, `busy`, `closed`, `failed` and `invalid_read_id`. Only `loaded` carries counts; nothing else can be shown as a stale or zero read. A valid empty ledger is a `loaded` zero.
- **Recorded rows, not activity.** Counts are retained recorded source rows, `exact` only for a complete clean scan of the whole ledger and otherwise `lower_bound`. Snapshot-wide diagnostics are apart from the window's per-mode counts, and a mode is a delivery mode, never an outcome. `latest_fires` (at most 100) and `observed_groups` (at most 100 observed `(rulebook, rule)` pairs of every in-window row, not active rules) carry separate `fires_truncated` and `groups_truncated`. Byte offsets are decimal strings.

Fixture mode has no native home, so its service has no source: every read answers `unavailable`/`not_configured` and never touches the user's home. The export carries that answer as `rule_activity`, read through the same service, and `FixtureDataSource` serves it. Browser preview offers no `ruleActivity`.

At startup the root route opens welcome only for a first launch — `app_info.had_indexed_history_at_startup` is false (read before the native index starts, since live counts race its initial scan) and the `xt.welcome.v1` completion, written only by welcome's Open Dashboard, is absent; otherwise, and for any later visit, it redirects to Dashboard. Explicit addresses are kept. Welcome shows the native index phase, Claude transcripts read (a file count, not progress toward a total), live database counts and each host's last-scan outcome, none of which claims an agent is installed or capturing. Unrecognized routes show a page-not-found placeholder. Sidebar selection and breadcrumb derive from the route; Settings and first launch do not highlight an unrelated navigation item. Query parameters are displayed as text only at this stage; there is no session filtering implementation yet.

Cmd+, opens Settings. Cmd+K focuses an enabled page Search if one is present; placeholder screens do not add an unwired search field. Appearance follows the existing system/light/dark preference and persistence behavior. A fixture badge uses `app_info.fixture`, so it also identifies native fixture runs. Missing host and capture data remain explicitly unknown rather than becoming fabricated zeros.

The Shell owns one selected range (7d default, 14d, 30d). The TopBar presets and the report-period label are shown on the routes whose numbers are measured over that window — Dashboard and Sessions; the custom-range control stays disabled. The same range keys the Dashboard report and its recorded token figures, and it is kept when navigating to other routes. The sidebar Usage widget reads provider-reported Claude and Codex account limits through `account_usage_read`, with no history-range input. The passive read refreshes Codex only. Claude is read by the app itself: at launch, then every ten minutes while the app runs, and when the user presses Refresh usage (`account_usage_refresh_claude`). One Claude read runs at a time. Each read starts the user's own Claude Code CLI (found on `PATH`, in `~/.local/bin`, `~/.claude/local`, `/opt/homebrew/bin` or `/usr/local/bin`) in a hidden terminal, in the dedicated empty folder `<app data folder>/xtrace-claude-usage-probe`, with the user's MCP servers left out (`--strict-mcp-config`), `--allowed-tools ""`, hooks disabled for that run (`disableAllHooks`) and Remote Control off, and types `/usage`. The probe sends no message to Claude, so it uses no quota. On the first run in that folder Claude Code asks whether to trust it; the app answers yes for its own probe folder only, which Claude Code records as an entry for that folder in `~/.claude.json`. Claude Code saves what `/usage` fetched as `cachedUsageUtilization` in its own config file (`~/.claude.json`, or `$CLAUDE_CONFIG_DIR/.claude.json`), which the app reads and never writes; it is used when it was saved after the read started, or when the panel shows its session and all-models week percents (Claude Code shows its saved copy when it fetched recently; model rows are not compared, since their labels differ); either way the reading's own fetch time is shown as its read time. Otherwise the rendered panel is read, and its read time is the moment the panel showed it ("Current session", "Current week (all models)", "Current week (<model>)", "N% used", "Resets …"), never the "What's contributing to your limits usage?" section below it. A reset shown as a clock time only is read relative to that moment (a time up to 15 minutes past is today's), and a session reset more than five hours away is not claimed. Only the session window, the all-models week and model weeks with a clear name (Claude Code's own model name, or Opus and Sonnet) are kept; other entries are dropped. A read is stopped after 25 seconds and Claude Code's whole process group is ended. If Claude Code saved a newer reading on its own within the last ten minutes (for example, the user ran `/usage`), the app uses it without starting a read. After each read the app deletes conversation files (`.jsonl`) Claude Code may have saved for that one probe folder under `~/.claude/projects`, and the session index never reads a Claude project folder whose name ends with `-xtrace-claude-usage-probe`. A failed read keeps the last good reading on screen, marked stale with its age, and the next automatic read waits 10, then 20, then 40, then at most 60 minutes, measured in wall-clock time so a read due while the Mac slept runs within a minute of waking; Refresh usage ignores that wait. If the automatic reader cannot start, Claude shows as unavailable rather than reading. Only when the user presses Refresh usage and the Claude Code read fails does the app fall back to reading Claude Code's Keychain login and asking the provider directly; automatic reads never touch the Keychain. The last good Claude reading (windows, percents, reset times and read time; no login, token or account identifier) is saved to `<app data folder>/claude-usage-last.json`, never the database, and shown as stale at the next launch until a new read succeeds; an unreadable or invalid file is ignored. Fixture mode never reads Claude. Each successful reading of either provider is also added to `<app data folder>/account-usage-history.jsonl`, never the database: one line per window with the provider, window keys, scope, name, percent used, reset time, window length and the reading's own read time (Claude Code's fetch time when the reading came from its saved copy); no login, token, email or account identifier. A window is not added again when the file already has a sample of it at or after that read time, when it is unchanged and under an hour has passed, or when it changed but under 15 minutes have passed; a new reset time is always added. Samples older than 60 days are dropped (the file is rewritten atomically about once a day, and at most 40,000 samples are kept); a damaged or half-written line is skipped and the file is rewritten whole at the next write; a file over 16 MB is not read and a new one is started. Fixture mode and tests write no history. From the current reading the app works out, for each window with a known reset and length (a session window without a stated length counts as five hours), its pace: once at least 3% of the window has passed, while something is used, the limit is not reached and the reset has not passed. The pace also gives the even-use point: the share of the window passed at the reading's own read time, times 100, unrounded (`expected_percent`). One rule decides everything: the rate is the percent used divided by the time since the window started, and the projection runs from the reading's own read time to the reset (percent used at the reset, at most 100). A run-out time is given exactly when the percent used is above `expected_percent`, at the time that rate reaches 100%, which is always before the reset. So the run-out warning, the bar's orange or green fill and the even-use mark always agree; a busy last few hours does not by itself raise a warning while the week as a whole is below even use. For each provider's all-models week it also gives use per local calendar day from the window's start through the reading's day: the rise within that day's readings plus the rise since the previous day's last reading (the window start counts as 0% on the first day when that day has a reading). A day without a reading is unknown, not zero; a day after an unknown day counts only its own readings and is marked as a lower bound, and is unknown when it has only one reading (nothing earlier to compare against). For the all-models week it also gives the week's readings as a series: this window's saved readings from the window's start (same reset, earlier than the reading; a previous window's readings are left out) followed by the current reading, oldest first, thinned evenly to at most 200 points while keeping the first and the current reading. Pace, daily use and the series are worked out on each read and never saved with the last reading. The widget's header has two icon buttons after `Usage`. The first, named `How the forecast works`, opens a short note on hover, on keyboard focus, or with a click or Enter. A click or Enter keeps the note open, including one already opened by hover or focus, until the next click or Enter, Escape, a press elsewhere, or hovering the refresh button (only one tooltip shows at a time); a note opened by keyboard focus also stays open when the pointer passes over the button and leaves, and closes when focus moves away; the note is drawn outside the sidebar card and says in plain words how often usage is read, how the speed and the projection are worked out, what the even-use mark means, and that a steady pace is assumed. The second, named `Refresh usage` with a matching tooltip, starts a read; while a read runs it is disabled, named `Reading usage…`, and its icon spins (or, when the system asks for reduced motion, fades instead). The sidebar shows the most used all-model window for each provider as percent remaining with a matching thin bar and one short line in local time without a time-zone name, for example `Week · resets Mon 8 PM` (`today 1:10 PM` for a reset today, the weekday within six days, else the date, such as `Oct 12`); the reading's age is added only when it is at least five minutes old or stale, for example `Week · resets Mon 8 PM · 12 min ago`. Under it, the all-models week's pace reads `Runs out ~Sat 3 PM` in the warning color when use is above even use, `Behind pace · ~68% used by reset` when it is below, or `On pace · ~68% used by reset` when exactly even (the same comparison as the even-use mark and the bar color) (prefixed `Week` when the main row shows another window); it is hidden when there is no pace, and a run-out time that has already passed (possible for a stale reading) is not shown. While that line is shown and the main bar is the all-models week itself, the bar carries a short even-use mark. The bar fills with what remains, so the mark sits at 100% minus `expected_percent` (40% of the week passed puts it at 60%). The mark is a focusable control whose name and tooltip (on hover and on keyboard focus, drawn outside the sidebar card) read exactly one of `6% ahead of pace` (percent used above even use, rounded; ahead means using faster than even, exactly when the bar is orange and a run-out time is shown), `3% behind pace`, `<1% ahead of pace` or `<1% behind pace` for a gap under 1 point, or `On pace` (exactly even). The same text is part of the row's screen-reader description. Clicking or pressing it does not open or close the row. When the main bar shows another window, such as a fuller session, no mark is drawn. Keyboard-accessible details open under each provider's row. For Codex they list every available window, including model-specific limits, each with its reset and pace. The main row's own window is not listed again when the header already says everything its row would (its percent, reset and its own pace: the main window is the all-models week, or has no pace of its own); its charts are then shown first, above the other windows. A fuller session in the main row keeps its own row only when it has a pace of its own, since the header's pace line is then the week's; without one, its row would only repeat the header and is left out. For Claude the details list no window rows at all (no session and no model-specific limits, such as `Fable · Week`): they show only the all-models week's charts and the reading's time, whatever window the header shows; a fuller session in the header keeps its header line and the week's `Week runs out …` pace line, as above. For the all-models week the details show a small burndown of the percent remaining over the week on a fixed 0–100% scale (labeled `100%` and `0%` on the left, each local midnight ticked along the bottom with the day's letter, or its short name when there is room): the series as a solid line, never drawn where there was no reading, when it has at least two readings spanning at least 2% of the window; otherwise the latest reading as a dot labeled with its percent remaining (left of the dot, or early in the week above it, or below it when near the top, never where the pace line runs), and the legend says `Latest reading` instead of `Remaining`. ## Verification

Run the browser suites sequentially; they start and stop their own servers:

```sh
pnpm check
pnpm e2e
pnpm e2e:production
```

The default suite includes the shell and all component tests on port 5174 (`E2E_PORT` overrides it). The production suite uses port 5194 (`E2E_PRODUCTION_PORT`). Both share a test-results directory, so run them sequentially. The shell cases run Chromium and WebKit with a 1120×720 viewport and F1 selected. The production suite builds with the fixture flag set, inspects emitted assets, then opens that actual production build in both browsers and checks the unavailable preview. Neither suite emulates Tauri IPC. Browser evidence does not establish native window behavior or an actual Safari 17 platform-floor run.

Rust-dependent DTO generation, fixture parity, license notices and native builds run through the local macOS checkpoint described in [CI](CI.md). The default `pnpm test` and hosted UI job do not require a native toolchain.

The implementation follows the pinned library APIs for [React Router declarative routing](https://reactrouter.com/start/declarative/routing), [TanStack Query invalidation](https://tanstack.com/query/v5/docs/framework/react/guides/query-invalidation), and [query cancellation](https://tanstack.com/query/v5/docs/framework/react/guides/query-cancellation).
